# JavaScript var · let · const

## 잘 알고 있는지

- var는 옛날 거고 호이스팅 문제 있으니 쓰지 말라.
- let은 변수, const는 상수
- 엄밀히 말해서 const는 상수가 맞을지
- 또 호이스팅, TDZ 등 처음에 어물쩡 넘어갔던 부분도 확실히 잡고싶다.

## 답을 본 뒤 알게 된 것

### 0. 서론

- 용어 정의

- 스코프(scope): 식별자가 유효한 범위. 코드의 어느 위치에서 그 이름으로 값에 접근할 수 있는지를 결정한다.
- 선언(declaration): 식별자를 스코프에 등록하는 것. "이 이름이 존재한다"를 알리는 행위.
- 초기화(initialization): 등록된 식별자에 값을 넣을 공간을 확보하고 값을 넣는 것.
- 할당(assignment): 이미 초기화된 식별자의 값을 바꾸는 것.

- 선언과 초기화는 별개의 단계. var와 let의 차이가 이 지점으로부터 시작된다.

### 1. var의 문제 3개

- `let`과 `const`가 ES6(2015)에 추가된 이유는, `var`에 세 가지 구조적 문제가 있었기 때문이다.

#### 1-1. 함수 스코프

```js
function f() {
  if (true) {
    var x = 1;
  }
  console.log(x); // 1
}
```

- var의 스코프 단위는 함수다. 블록({})은 스코프를 만들지 않는다.
- if 블록 안에서 선언했는데 블록 밖에서 접근된다. var에게 블록은 스코프 경계가 아니기 때문이다.
- let은 블록 스코프다.

```js
function f() {
  if (true) {
    let y = 1;
  }
  console.log(y); // ReferenceError: y is not defined
}
```

- 여기서 스코프를 만드는 것들을 구분해야 한다.

| 구문                      | var 기준    | let/const 기준 |
| ------------------------- | ----------- | -------------- |
| 함수 본문                 | 스코프 생성 | 스코프 생성    |
| 블록 `{}`                 | 생성 안 함  | 스코프 생성    |
| `if`, `for`, `while` 블록 | 생성 안 함  | 스코프 생성    |

- 왜 문제인가: 반복문 카운터 변수가 함수 전체에 노출된다. 블록 안에서만 쓰려고 만든 임시 변수가 밖으로 새어나가 이름 충돌을 일으킨다.

#### 1-2. 재선언 허용

```js
var x = 1;
var x = 2;
console.log(x); // 2
```

- 같은 스코프에서 같은 이름을 var로 다시 선언해도 에러가 나지 않는다.
- 두 번째 var x는 선언으로서는 무시되고 할당만 일어난다. 에러도, 경고도 없다.
- let은 재선언이 문법 오류다.

```js
let y = 1;
let y = 2; // SyntaxError: Identifier 'y' has already been declared
```

- 왜 문제인가: 긴 함수에서 이미 존재하는 변수 이름을 모르고 다시 선언하면, 원래 값이 조용히 덮인다. 에러가 나지 않으므로 실행해도 문제를 발견할 수 없다.
- SyntaxError라는 점도 짚어둘 만하다. 실행 전 파싱 단계에서 잡히므로 해당 코드가 실행되지 않아도 에러가 난다.

#### 1-3. 전역 객체의 프로퍼티가 된다.

```js
var a = 1;
console.log(window.a); // 1
```

- 전역 스코프에서 var로 선언하면 그 식별자가 전역 객체(브라우저에서 window)의 프로퍼티로 등록된다.

```js
let b = 2;
console.log(window.b); // undefined
```

- let/const는 그렇지 않다.
- 전역 let/const는 전역 스코프에 등록되지만 전역 객체의 프로퍼티는 아니다. 별도의 저장 공간에 들어간다.

- 왜 문제인가: 전역 객체에는 이미 수많은 표준 프로퍼티가 있다. var name = "hyun"처럼 흔한 이름을 쓰면 브라우저 내장 프로퍼티를 덮어쓸 수 있다. 그리고 여러 스크립트가 같은 전역 객체를 공유하므로 충돌 범위가 페이지 전체가 된다.

#### 1-4. 정리

|                    | var  | let         | const       |
| ------------------ | ---- | ----------- | ----------- |
| 스코프             | 함수 | 블록        | 블록        |
| 재선언             | 허용 | SyntaxError | SyntaxError |
| 재할당             | 허용 | 허용        | TypeError   |
| 전역 객체 프로퍼티 | 됨   | 안 됨       | 안 됨       |

- let과 const의 차이는 재할당 가능 여부 하나뿐이다. 스코프 규칙은 완전히 같다. 4장에서 이 "재할당 금지"가 정확히 무엇을 막는지 다룬다.

### 2. 호이스팅

#### 2-1. 호이스팅이란 무엇인가

- 호이스팅이란? 선언된 식별자가 코드 실행 전에 스코프에 등록되어, 실제 선언문보다 앞선 위치에서도 그 식별자가 존재하는 것으로 취급되는 현상.
- 흔히 "선언이 위로 끌어올려진다"고 설명되지만 코드가 이동하는 것이 아니다. 실제로 일어나는 일은 이렇다.
- JS 엔진은 코드를 실행하기 전에 해당 스코프를 훑어서 선언된 식별자를 전부 수집해 등록한다. 이것이 생성 단계다. 그 다음 코드를 위에서 아래로 실행하는 실행 단계가 온다.

```
생성 단계: 스코프 안의 선언을 수집해 등록
실행 단계: 코드를 순서대로 실행 (할당은 여기서)
```

- 선언은 생성 단계에서 처리되고, 할당은 실행 단계에서 그 줄에 도달할 때 처리된다. 이 시차가 호이스팅의 실체다.

- var, let, const, function, class. 전부 호이스팅된다. 즉 셋 다 생성 단계에서 등록된다. 차이는 등록될 때 초기화가 함께 되는지 여부다.

#### 2-2. 세 키워드의 차이

| 키워드 | 생성 단계에서               | 실행 단계에서                   |
| ------ | --------------------------- | ------------------------------- |
| var    | 등록 + `undefined`로 초기화 | 선언문에 도달하면 할당          |
| let    | 등록만. 초기화 안 됨        | 선언문에 도달하면 초기화 + 할당 |
| const  | 등록만. 초기화 안 됨        | 선언문에 도달하면 초기화 + 할당 |

```js
console.log(x); // undefined
var x = 1;
console.log(x); // 1
```

- var는 등록과 동시에 undefined가 들어간다. 그래서 선언문 전에 접근해도 값이 있다.

```js
console.log(y); // ReferenceError: Cannot access 'y' before initialization
let y = 1;
```

- let은 등록만 되고 초기화되지 않는다. 초기화되지 않은 식별자에 접근하면 에러가 난다.

- 에러 메시지를 정확히 읽어야 한다. y is not defined가 아니라 Cannot access 'y' before initialization 이다. 두 메시지가 다른 상황을 가리킨다.

```
y is not defined -> 식별자가 스코프에 없다
Cannot access 'y' before initialization -> 식별자가 스코프에 있는데 초기화 전이다
```

- 후자가 나온다는 것 자체가 let이 호이스팅됐다는 증거. 등록이 안 됐다면 엔진은 y라는 이름을 모르므로 is not defined를 냈을 것이다.
- 이 상태를 TDZ라고 부르고 3장에서 다룬다.

#### 2-3. 스코프 밖 접근과의 구분

```js
// 케이스 A — 스코프에 없음
{
  let a = 1;
}
console.log(a); // ReferenceError: a is not defined

// 케이스 B — 스코프에 있지만 초기화 전
console.log(b); // ReferenceError: Cannot access 'b' before initialization
let b = 1;
```

| 케이스 | 식별자 등록       | 원인          | 메시지                                    |
| ------ | ----------------- | ------------- | ----------------------------------------- |
| A      | 안 됨 (스코프 밖) | 존재하지 않음 | `is not defined`                          |
| B      | 됨                | 초기화 전     | `Cannot access ... before initialization` |

#### 2-4. 함수 선언문은 다르다

```js
f(); // 정상 동작
function f() {
  console.log("ok");
}
```

- function 선언문은 생성 단계에서 함수 객체까지 완성되어 등록된다. 등록 + 초기화 + 할당이 전부 생성 단계에서 끝난다.

- 그래서 선언 위치보다 앞에서 호출할 수 있다.
- 반면 함수 표현식은 변수 선언 규칙을 따른다.

```js
g(); // TypeError: g is not a function
var g = function () {};
```

- var g는 undefined로 초기화되어 있고, undefined를 호출하려 해서 TypeError다. ReferenceError가 아니라는 점을 구분해야 한다. 식별자는 존재하고, 그 값이 함수가 아닐 뿐이다.

```js
h(); // ReferenceError: Cannot access 'h' before initialization
const h = function () {};
```

- const h는 TDZ에 있으므로 접근 자체가 막힌다.

#### 2-5. 정리

| 선언                     | 생성 단계 결과        | 선언 전 접근 시      |
| ------------------------ | --------------------- | -------------------- |
| `var x`                  | 등록 + undefined      | undefined            |
| `let x` / `const x`      | 등록만                | ReferenceError (TDZ) |
| `function f() {}`        | 등록 + 함수 객체 완성 | 정상 호출            |
| `var f = function(){}`   | 등록 + undefined      | TypeError (호출 시)  |
| `const f = function(){}` | 등록만                | ReferenceError (TDZ) |

- 셋 다 호이스팅되지만, var만 등록 시점에 초기화된다.

### 3. TDZ (Temporal Dead Zone)

#### 3-1. 정의

- TDZ: 스코프에 등록된 식별자가 아직 초기화되지 않은 구간. 이 구간에서 해당 식별자에 접근하면 ReferenceError가 발생한다.

- 구간의 시작과 끝이 정해져 있다.

```
시작: 스코프 진입 (생성 단계에서 등록되는 시점)
끝:   선언문이 실행되어 초기화되는 시점
```

```js
{
  // ─── 여기부터 TDZ 시작 (x는 등록되어 있음)
  console.log(x); // ReferenceError

  let x = 1; // ─── 여기서 TDZ 종료

  console.log(x); // 1
}
```

- 이름의 "Temporal"이 중요하다. 공간(코드 위치)이 아니라 시간(실행 시점) 을 기준으로 하는 구간이다. 물리적으로 선언문 위에 있는 코드가 아니라, 초기화보다 먼저 실행되는 코드가 TDZ에 걸린다.

```js
function f() {
  return x; // 이 줄은 선언문보다 위에 있지만
}
let x = 1;
f(); // 호출 시점에는 이미 초기화 완료 → 정상 동작
```

- f 내부의 return x는 코드 위치상 선언문 앞에 있지만, f() 호출이 초기화 이후에 일어나므로 에러가 나지 않는다. TDZ는 코드 줄 번호가 아니라 실행 순서로 판정된다.

#### 3-2. var와 왜 다른가

- 2장에서 본 대로 차이는 생성 단계의 초기화 여부다.

|         | 생성 단계                 | 선언 전 접근     |
| ------- | ------------------------- | ---------------- |
| `var x` | 등록 + `undefined` 초기화 | `undefined` 반환 |
| `let x` | 등록만                    | `ReferenceError` |

- `var`는 TDZ가 없다. 정확히 말하면 **TDZ의 길이가 0이다** — 등록되는 순간 초기화도 끝나므로 "등록됐지만 초기화 안 된 구간"이 존재하지 않는다.

#### 3-3. TDZ가 존재하는 이유

- `var`처럼 `undefined`로 초기화해두면 에러가 안 나서 편할 것 같지만, ES6 설계자들은 의도적으로 에러를 내도록 했다. 이유 두 가지.

**첫째, `undefined`가 두 가지를 뜻하게 되는 문제.**

```js
var x;
console.log(x); // undefined — 값을 안 넣은 건가?

console.log(y);
var y = 1; // undefined — 아직 실행이 안 닿은 건가?
```

- `var`에서는 "선언만 하고 값을 안 넣은 상태"와 "선언문에 아직 도달하지 않은 상태"가 똑같이 `undefined`로 보인다. 구분할 방법이 없다.
- `let`은 후자를 에러로 만들어 이 모호함을 없앤다. `undefined`가 나오면 그건 명시적으로 값이 없는 것이다.

**둘째, `const`가 성립하기 위해 필요하다.**

```js
const x = 1;
```

- `const`는 재할당을 금지한다. 그런데 `var` 방식이라면 생성 단계에서 `undefined`가 들어가고, 선언문에서 `1`을 넣는 것이 **두 번째 값 설정**이 된다. 이건 재할당이므로 `const`의 규칙에 위배된다.
- TDZ가 있으면 초기화가 선언문에서 딱 한 번만 일어나므로 이 모순이 사라진다. `const`가 반드시 선언과 동시에 초기화되어야 하는 것(`const x;`는 `SyntaxError`)도 같은 이유다.
- 즉 **TDZ는 `const`를 가능하게 하려고 도입된 구조**이고, `let`은 일관성을 위해 같은 규칙을 따른다.

#### 3-4. 에러 메시지 3종 구분

- `ReferenceError`가 나오는 상황이 두 가지, 유사하게 헷갈리는 것이 하나 더 있다. 셋을 구분해야 한다.

```js
// ① 스코프에 없음
console.log(a);
// ReferenceError: a is not defined

// ② 스코프에 있지만 TDZ
console.log(b);
let b = 1;
// ReferenceError: Cannot access 'b' before initialization

// ③ 값이 undefined인데 호출/접근 시도
c();
var c = function () {};
// TypeError: c is not a function
```

|     | 등록 | 초기화          | 에러                                                  |
| --- | ---- | --------------- | ----------------------------------------------------- |
| ①   | ✗    | ✗               | `ReferenceError: is not defined`                      |
| ②   | ✓    | ✗               | `ReferenceError: Cannot access before initialization` |
| ③   | ✓    | ✓ (`undefined`) | `TypeError`                                           |

- ②의 메시지가 `is not defined`가 아니라는 점이 `let`도 호이스팅된다는 직접적인 증거다. 등록조차 안 됐다면 엔진은 그 이름을 모르므로 ①의 메시지를 냈을 것이다.

#### 3-5. typeof도 막힌다

- `typeof`는 선언되지 않은 식별자에 써도 에러가 나지 않는 유일한 연산자다.

```js
typeof undeclared; // "undefined" — 에러 없음
```

- 이 특성 때문에 `typeof`로 변수 존재 여부를 안전하게 확인하는 패턴이 있었다. 그런데 **TDZ에서는 이것도 에러가 난다.**

```js
typeof x; // ReferenceError: Cannot access 'x' before initialization
let x = 1;
```

- TDZ 접근 금지가 `typeof`보다 우선한다. 즉 `let`/`const`에 대해서는 "안전한 존재 확인" 방법이 없다.

#### 3-6. 함수 매개변수의 TDZ

- 기본값이 있는 매개변수끼리도 TDZ가 적용된다. 매개변수는 왼쪽에서 오른쪽으로 초기화되므로, 아직 초기화되지 않은 뒤쪽 매개변수를 참조할 수 없다.

```js
function f(a = b, b = 2) {}
f(); // ReferenceError: Cannot access 'b' before initialization

function g(a = 1, b = a) {}
g(); // 정상 — a가 먼저 초기화됨
```

#### 3-7. 정리

- TDZ = 등록됐지만 초기화되지 않은 구간
- 코드 위치가 아니라 **실행 시점** 기준
- `var`는 TDZ 길이가 0 (등록과 초기화가 동시)
- 존재 이유: `undefined`의 의미 모호성 제거 + `const` 성립
- `typeof`도 우회 못 함
- 에러 메시지로 "스코프에 없음"과 "TDZ"를 구분할 수 있다

### 4. const가 막는 것

#### 4-1. const는 재할당만 금지한다

- `const`가 금지하는 것은 **식별자에 대한 재할당** 하나다. 값 자체를 불변으로 만드는 것이 아니다.

```js
const x = 1;
x = 2; // TypeError: Assignment to constant variable.
```

- 에러 종류를 짚어두자. `SyntaxError`가 아니라 **`TypeError`** 다. 즉 파싱 단계가 아니라 **실행 중**에 발생한다. 재할당 문장에 실제로 도달해야 에러가 난다.

```js
const y = 1;
if (false) {
  y = 2; // 실행되지 않으므로 에러 없음
}
```

- 1장에서 본 재선언 에러(`SyntaxError`)와 다르다.

| 위반                                  | 에러          | 발생 시점 |
| ------------------------------------- | ------------- | --------- |
| 재선언 (`let x` 두 번)                | `SyntaxError` | 파싱 단계 |
| 재할당 (`const x = ...` 후 `x = ...`) | `TypeError`   | 실행 중   |

#### 4-2. 객체 내부 변경은 막지 않는다

- `const`로 선언한 변수가 객체를 참조할 때, 그 객체의 프로퍼티는 자유롭게 바꿀 수 있다.

```js
const obj = { a: 1 };

obj.a = 2; // 정상
obj.b = 3; // 정상
delete obj.a; // 정상

obj = {}; // TypeError — 재할당은 금지
```

```js
const arr = [1, 2];

arr.push(3); // 정상
arr[0] = 99; // 정상
arr.length = 0; // 정상

arr = []; // TypeError
```

- **왜 이렇게 되는가:** 변수에 저장되는 것은 객체 자체가 아니라 객체에 대한 **참조**다. `const`는 그 변수가 담고 있는 참조가 다른 참조로 바뀌는 것을 막는다. 참조가 가리키는 대상의 내부 상태는 `const`의 관할이 아니다.
- 프리미티브 값에서 `const`가 불변처럼 보이는 것은 프리미티브 자체가 불변이기 때문이고, `const`의 효과가 아니다.

#### 4-3. Object.freeze와의 차이

- 객체 내부를 막고 싶으면 `Object.freeze`를 쓴다. 이것이 `const`와 다른 층에서 작동한다.

```js
const obj = Object.freeze({ a: 1 });

obj.a = 2; // 무시됨 (strict mode에서는 TypeError)
obj.b = 3; // 무시됨
delete obj.a; // 무시됨

obj = {}; // TypeError — 이건 const가 막은 것
```

- 두 메커니즘이 서로 다른 것을 막는다.

|                 | 막는 대상            | 작동 층     |
| --------------- | -------------------- | ----------- |
| `const`         | 식별자의 재할당      | 변수 바인딩 |
| `Object.freeze` | 객체의 프로퍼티 변경 | 객체 자체   |

- 둘은 대체 관계가 아니라 조합 관계다. 완전히 고정하려면 둘 다 필요하다.

**`Object.freeze`의 특성 두 가지**

- **첫째, non-strict mode에서는 조용히 실패한다.** 에러 없이 변경이 무시된다. 모듈이나 `class` 내부는 자동으로 strict mode이므로 `TypeError`가 난다.
- **둘째, 얕다(shallow).** 최상위 프로퍼티만 동결한다.

```js
const obj = Object.freeze({ inner: { a: 1 } });

obj.inner = {}; // 무시됨
obj.inner.a = 2; // 정상 동작 — 중첩 객체는 동결 안 됨
```

- 깊은 동결이 필요하면 재귀적으로 `Object.freeze`를 적용해야 한다.

```js
function deepFreeze(obj) {
  Object.values(obj).forEach((v) => {
    if (typeof v === "object" && v !== null) deepFreeze(v);
  });
  return Object.freeze(obj);
}
```

- `Object.isFrozen(obj)`으로 동결 여부를 확인할 수 있다.

#### 4-4. const는 선언과 동시에 초기화해야 한다

```js
const x; // SyntaxError: Missing initializer in const declaration
let y; // 정상 — undefined
```

- 3장에서 본 이유와 같다. `const`는 초기화가 정확히 한 번만 일어나야 하므로, 선언 시점에 값이 없으면 나중에 넣을 방법이 없다. 그래서 문법 자체가 금지한다.

#### 4-5. 예외 — 반복문의 const

- `for...of`와 `for...in`에서는 `const`를 쓸 수 있다.

```js
for (const item of [1, 2, 3]) {
  console.log(item); // 1, 2, 3
}
```

- 재할당처럼 보이지만 아니다. **반복마다 새로운 바인딩이 생성**되기 때문에 각각이 별개의 `const`다. 5장에서 다룰 `let`의 반복문 동작과 같은 메커니즘이다.
- 반면 일반 `for` 문에서는 쓸 수 없다.

```js
for (const i = 0; i < 3; i++) {} // TypeError — i++가 재할당
```

- 일반 `for` 문의 카운터는 같은 바인딩을 계속 갱신하는 구조이므로 재할당이 발생한다.

#### 4-6. 무엇을 기본으로 쓸 것인가

- `const` → 재할당이 필요하면 `let` → `var`는 쓰지 않는다.
- `const`를 기본으로 두는 이유는 불변성 보장이 아니라 **읽는 사람에게 "이 식별자는 이 값을 계속 가리킨다"는 정보를 주기 때문**이다. 코드를 읽을 때 추적해야 할 상태가 줄어든다.
- `const`가 값의 불변을 보장하지 않는다는 점을 정확히 알고 있어야 이 관용구를 오해 없이 쓸 수 있다.

#### 4-7. 정리

- `const`가 막는 것은 재할당 하나. `TypeError`, 실행 중 발생
- 객체 프로퍼티 변경은 막지 않음 — 참조가 고정되는 것이고 대상 내부는 관할 밖
- `Object.freeze`는 다른 층에서 객체 내부를 막음. 얕고, non-strict에서는 조용히 실패
- 선언과 동시에 초기화 필수 (`const x;`는 `SyntaxError`)
- `for...of`/`for...in`에서는 반복마다 새 바인딩이 생겨 `const` 사용 가능

### 5. 반복문 + 클로저

#### 5-1. 현상

- 같은 구조의 코드에서 `var`와 `let`이 다른 결과를 낸다.

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));
}
// 3 3 3
```

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));
}
// 0 1 2
```

- `var`는 `3`을 세 번 출력한다. 반복문이 세 번 돌았는데도 세 콜백이 모두 같은 값을 본다.

#### 5-2. 왜 var는 3 3 3인가

- 두 가지가 겹쳐서 발생한다.

**첫째, `var i`는 함수 스코프이므로 바인딩이 하나뿐이다.**

- 반복이 세 번 돌아도 `i`라는 저장 공간은 하나다. 매 반복마다 그 하나의 값을 갱신한다.

```
반복 1: i = 0
반복 2: i = 1
반복 3: i = 2
종료 시: i = 3  ← i < 3이 거짓이 되어야 반복이 끝나므로
```

**둘째, 콜백은 값을 복사하지 않고 바인딩을 참조한다.**

- `() => console.log(i)`는 `i`의 현재 값을 캡처하는 것이 아니라, `i`라는 **식별자를 담고 있는 스코프를 참조**한다. 실행 시점에 그 스코프에서 `i`를 찾아 읽는다.

**셋째, `setTimeout` 콜백은 반복문이 끝난 뒤에 실행된다.**

- 07-23 이벤트 루프 노트의 내용이다. `setTimeout` 콜백은 태스크 큐에 들어가고, 콜 스택이 비어야 실행된다. 반복문은 동기 코드이므로 세 번 다 돌고 끝난 뒤에야 콜백이 실행된다.
- 세 조건을 합치면: 콜백이 실행되는 시점에 유일한 `i`는 이미 `3`이 되어 있고, 세 콜백이 모두 그 하나를 읽는다.
- `setTimeout` 없이 확인해보면 차이가 드러난다.

```js
for (var i = 0; i < 3; i++) {
  console.log(i); // 0 1 2 — 동기 실행이므로 그 시점의 값
}
```

- 동기 코드는 각 반복 시점에 즉시 읽으므로 정상이다. **비동기 콜백일 때만 문제가 된다.** 문제의 본질은 "읽는 시점"이다.

#### 5-3. 왜 let은 0 1 2인가

- `let`은 **반복마다 새로운 바인딩을 생성한다.**

```
반복 1: 새 바인딩 i₁ = 0  → 콜백 A가 i₁을 참조
반복 2: 새 바인딩 i₂ = 1  → 콜백 B가 i₂를 참조
반복 3: 새 바인딩 i₃ = 2  → 콜백 C가 i₃을 참조
```

- `i`라는 이름은 같지만 세 개의 별개 저장 공간이다. 각 콜백이 서로 다른 바인딩을 참조하므로, 나중에 실행되어도 각자 자기 값을 읽는다.
- 이것은 블록 스코프의 자동 결과가 아니라 **`for` 문에 대해 스펙에 명시된 특별 규칙**이다. 반복문의 각 이터레이션마다 이전 바인딩의 값을 복사한 새 바인딩을 만든다.
- 4장 5절에서 `for...of`에 `const`를 쓸 수 있는 이유가 이것이다. 재할당이 아니라 매번 새 바인딩이므로 `const`의 규칙에 위배되지 않는다.

#### 5-4. 클로저

- 여기서 클로저의 실체가 드러난다.
- **클로저**: 함수가 자신이 정의된 스코프를 계속 참조하여, 그 스코프가 생성된 실행 흐름이 종료된 뒤에도 해당 스코프의 식별자에 접근할 수 있는 것.

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));
}
```

- 각 반복의 블록 스코프는 반복이 끝나면 사라져야 한다. 그런데 사라지지 않는다. 콜백 함수가 그 스코프를 참조하고 있기 때문이다. 참조가 남아 있는 동안 스코프는 유지된다.
- 즉 클로저는 특별한 기능이 아니라 **스코프 참조가 끊기지 않는 상태**다. `var` 버전도 클로저다 — 다만 세 콜백이 참조하는 스코프가 하나여서 같은 값을 보는 것이다.

|       | 스코프 개수       | 콜백이 보는 것    |
| ----- | ----------------- | ----------------- |
| `var` | 1개 (함수 스코프) | 공유된 하나의 `i` |
| `let` | 3개 (반복별 블록) | 각자의 `i`        |

- 클로저의 유무가 아니라 **참조 대상이 몇 개인가**가 결과를 갈랐다.

#### 5-5. let 없이 해결하기

- ES6 이전에는 IIFE(즉시 실행 함수 표현식)로 스코프를 수동 생성했다.

```js
for (var i = 0; i < 3; i++) {
  (function (j) {
    setTimeout(() => console.log(j));
  })(i);
}
// 0 1 2
```

- `i`의 현재 값을 인자로 넘겨 매개변수 `j`에 받는다. 함수 호출마다 새로운 스코프가 생기고 `j`는 그 스코프에 속하므로, 반복마다 독립적인 바인딩이 만들어진다.
- `let`이 하는 일을 함수 호출로 수동으로 재현한 것이다. `let`의 반복별 바인딩 규칙은 이 패턴을 언어 차원에서 흡수한 결과다.

#### 5-6. 실무에서 마주치는 형태

- 이벤트 리스너 등록에서 같은 구조가 나온다.

```js
const buttons = document.querySelectorAll("button");

for (var i = 0; i < buttons.length; i++) {
  buttons[i].addEventListener("click", () => {
    console.log(i); // 모든 버튼이 buttons.length를 출력
  });
}
```

- 클릭은 반복문이 끝난 뒤 발생하므로 모든 리스너가 최종값을 읽는다. `let`으로 바꾸면 해결된다.
- `forEach`를 쓰면 이 문제가 애초에 발생하지 않는다.

```js
buttons.forEach((btn, i) => {
  btn.addEventListener("click", () => console.log(i));
});
```

- `forEach`는 콜백 함수를 호출하는 구조이므로 반복마다 새로운 함수 스코프가 생기고, `i`는 매개변수로 그 스코프에 속한다. IIFE 패턴이 내장된 형태다.

#### 5-7. 정리

- `var`의 `3 3 3`은 세 가지가 겹친 결과: 단일 바인딩 + 스코프 참조 + 비동기 실행 시점
- 동기 코드에서는 문제가 드러나지 않는다. 읽는 시점이 뒤로 밀릴 때만 발생
- `let`은 반복마다 새 바인딩을 생성한다 (`for` 문에 대한 스펙 명시 규칙)
- 클로저는 스코프 참조가 끊기지 않는 상태. 두 경우 모두 클로저이며, 참조 대상 개수가 결과를 가른다
- `forEach`나 IIFE는 함수 호출로 스코프를 만들어 같은 효과를 낸다

### 6. 면접용 1분 답변

**Q. `var`와 `let`/`const`의 차이를 설명해주세요.**

크게 네 가지입니다. 스코프 단위, 재선언 허용 여부, 전역 객체 프로퍼티가 되는지, 그리고 호이스팅 시 초기화 여부입니다.

`var`는 함수 스코프여서 블록 안에서 선언해도 블록 밖에서 접근됩니다. `let`과 `const`는 블록 스코프입니다. 그리고 `var`는 같은 이름을 다시 선언해도 에러가 나지 않아서 기존 값이 조용히 덮이는데, `let`은 `SyntaxError`가 발생합니다. 전역에서 `var`로 선언하면 전역 객체의 프로퍼티가 되어 내장 프로퍼티와 충돌할 수 있지만, `let`과 `const`는 별도 공간에 등록됩니다.

가장 자주 오해되는 건 호이스팅입니다. `let`과 `const`도 호이스팅됩니다. 셋 다 생성 단계에서 스코프에 등록되는데, `var`만 그때 `undefined`로 초기화된다는 차이가 있습니다. `let`은 등록만 되고 초기화되지 않아서, 선언문 전에 접근하면 `Cannot access before initialization`이라는 `ReferenceError`가 납니다. 이 메시지가 `is not defined`가 아니라는 게 호이스팅이 일어났다는 증거입니다. 이 구간을 TDZ라고 부릅니다.

**Q. TDZ가 왜 필요한가요? (꼬리질문)**

두 가지 이유가 있습니다. 첫째로 `var`에서는 값을 안 넣은 상태와 선언문에 도달하지 않은 상태가 둘 다 `undefined`로 보여서 구분이 안 됐는데, TDZ가 후자를 에러로 만들어 모호함을 제거했습니다.

둘째는 `const` 때문입니다. `var` 방식이라면 생성 단계에서 `undefined`가 들어가고 선언문에서 값을 넣는 게 두 번째 값 설정, 즉 재할당이 됩니다. `const`의 규칙에 위배되죠. TDZ가 있으면 초기화가 선언문에서 한 번만 일어나므로 이 모순이 사라집니다. `const x;`가 `SyntaxError`인 것도 같은 이유입니다.

**Q. `const`로 선언한 배열에 `push`가 되는 이유는? (꼬리질문)**

`const`가 막는 것은 식별자의 재할당 하나입니다. 변수에 저장되는 건 객체 자체가 아니라 참조이고, `const`는 그 참조가 다른 참조로 바뀌는 것만 막습니다. 참조가 가리키는 대상의 내부 상태는 관할이 아닙니다.

객체 내부를 막으려면 `Object.freeze`를 써야 하는데, 이건 변수 바인딩이 아니라 객체 자체에 작용하는 다른 층의 메커니즘입니다. 다만 얕게 동결되므로 중첩 객체는 별도로 처리해야 하고, non-strict mode에서는 에러 없이 조용히 무시됩니다.

### 7. 한 줄 요약

> `var`와 `let`/`const`의 모든 차이는 **선언과 초기화가 언제 분리되는가**에서 나온다. 셋 다 생성 단계에 등록되지만 `var`만 그때 초기화되고, 그 시차가 TDZ이며, TDZ가 있어야 `const`가 성립한다.
