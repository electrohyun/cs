# 웹소켓 프레임 구조 (WebSocket Frame Structure)

## 잘 알고 있는지

- 프레임(Frame)은 OSI 7 Layer의 그것 아닌가 하는 생각이 들었다.
- 그러나 웹소켓 연결은 7계층, 응용 계층에 존재하는데 이게 뭐지 싶었다. 바로 학습 도전!

## 답을 본 뒤 알게 된 것

### 0. 프레임이 그 프레임인가?

- 계층이 다르다 — 웹소켓 프레임은 7계층, 이더넷 프레임은 2계층
- 포함 관계다 — 웹소켓 프레임이 이더넷 프레임 안에 (여러 겹을 거쳐) 담긴다
- 헤더 구조가 완전히 다르다 — MAC 주소 대신 FIN/opcode/MASK
- 공통점은 "스트림에 경계를 긋는다"는 목적뿐이다

### 1. 프레임 레이아웃

#### 1-1. 첫 바이트: FIN / RSV1·2·3 / opcode

```
0 1 2 3 4 5 6 7
 +-+-+-+-+-------+
 |F|R|R|R| opcode|
 |I|S|S|S|  (4)  |
 |N|V|V|V|       |
 | |1|2|3|       |
 +-+-+-+-+-------+
```

프레임의 맨 앞 1바이트(8bit)는 이렇게 쪼개진다.

1. FIN (1bit)

- 이 프레임이 메시지의 마지막 프레임인지를 나타낸다. 0은 뒤에 이어지는 프레임이 더 있다. 1은 이 프레임에서 메시지가 끝난다.
- 0은 꺼짐, 1은 켜짐을 연상하기 쉬운데, 이름이 FIN이다. FIN에 대해 false / true를 나타낸다고 이해해보려 한다.
- 프레임 하나로 끝나는 메시지는 FIN=1이다. 대부분의 경우가 여기 해당한다. FIN=0은 4장 fragmentation에서 다룬다.

2. RSV1, RSV2, RSV3 (각 1bit)

- 확장(extension)용 예약 비트다. 기본값은 000. 확장을 협상하지 않았는데 이 비트가 켜져 있으면 수신 측은 연결을 닫아야 한다.
- 실제로 쓰이는 사례는 permessage-deflate 압축 확장이고, 이때 RSV1=1이 "이 프레임의 페이로드는 압축되어 있다"는 뜻이 된다. 오늘은 여기까지만.

3. opcode (4bit)

- 이 프레임이 무엇인지를 나타낸다. 4bit이므로 0x0~0xF 범위. 2장에서 값별로 다룬다.

#### 1-2. 둘째 바이트: MASK / Payload length

```
0 1 2 3 4 5 6 7
 +-+-------------+
 |M| Payload len |
 |A|     (7)     |
 |S|             |
 |K|             |
 +-+-------------+
```

1. MASK (1bit)

- 페이로드가 마스킹되어 있는지를 나타낸다.
- 0이면 마스킹되어있지 않다. "Masking-key 필드가 없다".
- 1이면 마스킹되어있다. "Masking-key 필드가 뒤에 있다".
- 이 비트가 Masking-key 필드의 존재 여부를 결정한다는 점이 중요하다. 프레임 길이가 이 비트에 따라 4바이트 달라진다. 마스킹 규칙 자체는 3장에서 다룬다.

2. Payload length (7bit)

- 7bit이므로 표현 범위는 0~127. 그런데 이 값이 그대로 길이가 아닌 경우가 있다. 다음 절.

#### 1-3. 확장 길이 필드

- 7bit 값을 읽고 세 갈래로 분기한다.

| 7bit 값 | 실제 길이         | 추가 필드 |
| ------- | ----------------- | --------- |
| 0 ~ 125 | 그 값 자체        | 없음      |
| 126     | 뒤따르는 16bit 값 | 2바이트   |
| 127     | 뒤따르는 64bit 값 | 8바이트   |

- 즉 126과 127은 길이가 아니라 "뒤를 더 읽어라"는 지시자다.
- 읽는 순서로 정리하면 이렇다.

```
1. 둘째 바이트의 하위 7bit를 읽는다
2. 125 이하면 → 그게 길이다. 끝
3. 126이면 → 다음 2바이트를 부호 없는 정수로 읽는다. 그게 길이다
4. 127이면 → 다음 8바이트를 부호 없는 정수로 읽는다. 그게 길이다
```

- "확장 길이 필드는 네트워크 바이트 순서(big-endian) 로 해석한다. 최상위 바이트가 먼저 온다.".

- 주의할 점 2가지:
- 127을 쓸 때 64bit의 최상위 비트는 0이어야 한다. 즉 실제 상한은 2^63-1
- 표현 가능한 최소 형식을 써야 한다. 길이가 100인데 126 형식으로 보내면 규칙 위반이다.

- 왜 3단계로 나눴는지는 오늘 범위 밖. 읽는 방법까지만 확정하고 넘어간다고 한다.

#### 1-4. Masking-key

- MASK=1일 때만 존재하는 32bit(4바이트) 필드다. 확장 길이 필드 바로 뒤에 온다.
- MASK=0이면 이 필드는 아예 없다. 존재하지 않는 것이지 0으로 채워지는 것이 아니다.

#### 1-5. Payload data

- 실제 내용. 앞에서 확정한 payload length만큼의 바이트다.

- 정확히는 Extension data + Application data 로 구성되고, payload length는 이 둘의 합이다. 확장을 협상하지 않았다면 Extension data는 길이 0이므로 페이로드 전체가 Application data다.

#### 전체 순서 정리

```
[1바이트]  FIN + RSV1~3 + opcode
[1바이트]  MASK + Payload length(7bit)
[0/2/8바이트]  확장 길이 (7bit 값이 126 또는 127일 때만)
[0/4바이트]  Masking-key (MASK=1일 때만)
[N바이트]  Payload data
```

- 최소 헤더는 2바이트, 최대 헤더는 14바이트(2 + 8 + 4)다.

#### 확인 문제

- 문제 1

```
10000001  00000101  [뒤에 5바이트]
```

1. FIN은?

- 1이다. FIN이 true라는 뜻이므로, 다음 메세지는 없다.

2. opcode는? 무슨 프레임인가?

- 첫 바이트 안의, 뒤 4바이트이므로, 0001이다.

3. MASK는?

- 둘째 바이트에서 등장한다. 페이로드가 마스킹되어 있는지를 판단한다.
- 둘째 바이트의 첫번째 자리. 0이다. 마스킹 되어있지 않다.

4. payload length는?

- 0000101, 즉, 5바이트.

5. Masking-key 필드가 있나?

- MASK가 1일때만 있다. 그러나 현재 0이므로, 마싕 키 필드는 없다. 0으로 채워진 것도 아니고, 없다.

6. 헤더는 총 몇 바이트인가?

- 2바이트.

- 문제 2

```
00000010  11111110  00000001  00000000  ...
```

7. FIN은? 이게 의미하는 바는?

- 첫 바이트의 첫 문자, 즉 FIN은 0이다. FIN이 false라는 것은, 뒤에 메시지가 더 있다는 뜻이다.

8. opcode는? 무슨 프레임인가?

- opcode는 첫 바이트의 뒤의 4자리이며, 0010이다.

9. MASK는?

- 둘째 바이트의 첫번째 문자가 MASK이며, 1이다. true이다. 즉, 마스킹 되어있음을 의미한다 (주어: ?)

10. payload length는 몇 바이트인가?

- 1111110, 126. 뒤의 2바이트를 더 읽으라는 지시이므로,

```
00000001 00000000 = 0000000100000000(2) = 256
```

페이로드 렝스는 256바이트.

11. 헤더 전체 길이는?

- 첫 바이트 1
- 둘째 바이트 1
- 확장 길이 2 (값이 126이므로)
- Masking-key 4 (MASK=1이므로)

- 8바이트.

- 문제 3

```
10001000  00000010  [뒤에 2바이트]
```

12. FIN, opcode는? 무슨 프레임인가?

- FIN은 1. 뒤에 메시지가 더 안온다. opcode는 1000.

13. MASK는?

- MASK는 0. 마스킹되어있지 않다.

14. 이 프레임이 규칙을 지키고 있나? (5장 컨트롤 프레임 제약 미리보기)

- 헤더 2 + 페이로드 2 = 4바이트

- 문제 4: 말로 답하기

```
"웹소켓 프레임의 최소 헤더 길이와 최대 헤더 길이는 얼마이며, 왜 그렇게 차이가 나는가?"
```

- 최소 2바이트, 최대 14바이트.

- 차이가 나는 이유는 두 필드가 조건부로 존재하기 때문이다.

1. 확장 길이 필드 (0 / 2 / 8바이트) — 7비트만으로는 125까지밖에 표현 못 한다. 그보다 긴 페이로드는 별도 필드가 필요하다. 짧은 메시지에까지 8바이트 길이 필드를 붙이면 낭비이므로, 길이에 따라 필요한 만큼만 붙인다.
2. Masking-key (0 / 4바이트) — 클라이언트가 보내는 프레임에만 필요하다. 서버가 보내는 프레임에는 없다.

> ⭐️ payload length 필드의 값은 7bit로 표현되지만, 그 값이 가리키는 단위는 바이트다.

### 2. opcode

- 첫 바이트의 뒤 4비트. 이 프레임이 무엇인지를 나타낸다고 했는데, 뭘까?

#### 2-1. 값 목록

| 비트 | Hex | 이름         | 분류   |
| ---- | --- | ------------ | ------ |
| 0000 | 0x0 | continuation | 데이터 |
| 0001 | 0x1 | text         | 데이터 |
| 0010 | 0x2 | binary       | 데이터 |
| 1000 | 0x8 | close        | 컨트롤 |
| 1001 | 0x9 | ping         | 컨트롤 |
| 1010 | 0xA | pong         | 컨트롤 |

- 나머지 값(0x3~0x7, 0xB~0xF)은 예약(reserved) 이다. 이 값을 받으면 수신 측은 연결을 닫아야 한다.

#### 2-2. 구조적 규칙: 최상위 비트가 분류다

- 4비트 중 첫 비트가 1이면 컨트롤 프레임이다.

```
0xxx → 데이터 프레임 (0x0 ~ 0x7)
1xxx → 컨트롤 프레임 (0x8 ~ 0xF)
```

- 우연이 아니라 의도된 설계다. 수신 측이 opcode 전체를 해석하기 전에 비트 하나만 보고 "이건 즉시 처리해야 하는 관리용 프레임"인지 판별할 수 있다.
- 이 분류가 5장 제약(125바이트 이하, 분할 불가)과 4장 규칙(fragment 시퀀스 중간에 컨트롤 프레임만 끼어들 수 있다)의 근거가 된다.

#### 2-3. 값별 의미

- 0x1 text — 페이로드가 UTF-8 문자열이다. 유효하지 않은 UTF-8이면 연결을 닫아야 한다. socket.send("hello")가 이걸 만든다.

- 0x2 binary — 페이로드가 임의 바이트열이다. 해석은 애플리케이션 몫이다. socket.send(arrayBuffer)가 이걸 만든다.

- 0x0 continuation — "앞 프레임의 연장"이라는 뜻이다. 자기 자신은 타입 정보를 갖지 않는다. text의 연장인지 binary의 연장인지는 시퀀스의 첫 프레임 opcode가 결정한다. 4장에서 다룬다.

- 0x8 close — 연결 종료 의사 표시. 페이로드에 상태 코드가 들어간다. 6장에서 다룬다.

- 0x9 ping / 0xA pong — 연결 생존 확인. ping을 받으면 반드시 pong으로 응답해야 하고, 이때 받은 페이로드를 그대로 되돌려준다.

- 요청받지 않은 pong(unsolicited pong)을 보내는 것도 허용된다. 응답을 기대하지 않는 단방향 하트비트로 쓰인다.

#### 2-4. 브라우저 API에서 안 보이는 것

- 브라우저의 WebSocket 객체에는 ping/pong을 보내는 메서드가 없다. socket.ping() 같은 건 존재하지 않는다.

- 브라우저가 ping을 받으면 자동으로 pong을 보내지만, 이는 JS 레이어에 노출되지 않는다. 즉 하트비트는 서버가 주도한다.

- Socket.IO가 자체 하트비트(Engine.IO 레벨의 ping/pong 패킷)를 따로 구현하는 이유가 이것이다. 웹소켓 프로토콜의 ping/pong과 Socket.IO의 하트비트는 다른 층에 있는 별개의 메커니즘이다.

- (개인 메모: smocket 관점에서 중요하다. 하트비트 타임아웃을 시뮬레이션할 때 어느 층의 ping/pong을 조작할 것인지를 정해야 한다.)

### 3. 마스킹

#### 3-1. 동작

- 클라이언트는 프레임마다 32비트 마스킹 키를 새로 생성하고, 페이로드의 각 바이트를 키의 바이트와 XOR한다.

```
transformed[i] = original[i] XOR key[i mod 4]
```

- 키가 4바이트이므로 페이로드 바이트를 4개 주기로 순환하며 적용한다. 0번 바이트는 key[0], 1번은 key[1], ... 4번은 다시 key[0].

- XOR은 자기역함수다. 같은 키로 한 번 더 XOR하면 원본이 돌아온다. 그래서 서버는 별도 복호화 로직 없이 동일한 연산을 반복하면 된다.

```
(A XOR K) XOR K = A
```

- 이건 암호화가 아니다. 마스킹 키가 프레임 헤더에 평문으로 그대로 실려 온다. 트래픽을 볼 수 있는 사람은 누구나 원본을 복원할 수 있다. 기밀성은 TLS(wss://)가 담당하고, 마스킹은 완전히 다른 목적이다.

#### 3-2. 방향 규칙

- 클라이언트 → 서버: 마스킹 의무
- 서버 → 클라이언트: 마스킹 금지

- 이 규칙 때문에 MASK 비트가 송신자를 식별하는 정보가 된다. 2장 확인 문제에서 나온 "주어는 누구인가"의 답이 이것이다.

- 위반 시 처리:

- 서버가 마스킹 안 된 프레임을 받으면 → 연결을 닫아야 한다
- 클라이언트가 마스킹된 프레임을 받으면 → 연결을 닫아야 한다

#### 3-3. 왜 의무인가: 캐시 포이즈닝

- 핵심 전제: 인터넷 중간에는 웹소켓을 모르는 프록시가 존재한다.

- 투명 프록시(transparent proxy)는 클라이언트가 존재를 인지하지 못한 채 경유하는 중계 서버다. ISP나 기업망에 흔히 있고, 오래된 것들은 HTTP만 안다.

공격 시나리오:

1. 공격자가 피해자 브라우저에서 악성 스크립트를 실행시킨다 (광고 등)
2. 스크립트가 공격자 서버로 웹소켓 연결을 연다. 핸드셰이크는 HTTP로 시작하므로 프록시를 정상 통과한다
3. 101 응답 이후 이 연결은 웹소켓이지만, 프록시는 그걸 이해하지 못하고 여전히 HTTP 연결로 취급한다
4. 스크립트가 웹소켓 페이로드로 이런 바이트열을 보낸다:

```
GET /script.js HTTP/1.1
Host: bank.example.com
```

5. 프록시는 이걸 새로운 HTTP 요청으로 오인한다
6. 공격자 서버가 이에 대한 응답으로 악성 JS를 반환하면, 프록시는 그것을 bank.example.com/script.js의 캐시로 저장한다
7. 같은 프록시를 쓰는 모든 사용자가 은행 사이트에 접속할 때 공격자의 스크립트를 받는다

- 한 번의 공격으로 프록시 뒤의 전체 사용자가 오염된다.

- 마스킹이 이걸 막는 방식:
- 공격이 성립하려면 공격자가 회선에 흐르는 바이트열을 정확히 통제할 수 있어야 한다. GET /script.js...라는 문자열이 그대로 나타나야 프록시가 요청으로 오인한다.

- 마스킹이 있으면:
- 키가 프레임마다 랜덤이다
- 공격자는 스크립트에서 socket.send()에 넘길 문자열은 정하지만, 브라우저가 어떤 키를 뽑을지는 모른다
- 회선에 나가는 실제 바이트는 매번 달라진다
- 즉 공격자가 페이로드는 정하지만 전송되는 바이트열은 정하지 못한다. 이 분리가 방어의 본질이다.
- 키가 공격자에게 보이는데 왜 막히냐는 반문이 나올 수 있다. 공격자가 나중에 트래픽을 읽는 건 문제가 아니다. 문제는 전송 시점에 원하는 바이트열을 만들어내는 것이고, 키가 브라우저 내부에서 랜덤 생성되므로 그게 불가능하다.

#### 3-4. 부수 효과

- 서버는 매 프레임 XOR 연산을 해야 한다. 소량의 CPU 비용
- 같은 내용을 보내도 프레임 바이트열이 매번 달라진다. 캡처한 트래픽을 눈으로 읽을 수 없다

- 두 번째가 smocket에서 의미가 있다. 개발자도구 Network 탭이 웹소켓 메시지를 보여줄 수 있는 건 브라우저가 마스킹 전/후 지점에서 값을 가져오기 때문이다. Wireshark로 회선을 캡처하면 마스킹된 바이트만 보인다. (07-17 노트 "mock 트래픽과 개발자도구 네트워크 탭"의 연장선)

#### 3-5. 확인문제

1. 마스킹의 목적은 무엇인가? 암호화인가?

- 목적은 캐시 포이즈닝 방어다. 암호화가 아니다! 키가 헤더에 평문으로 실려 오므로 누구나 복원할 수 있다. 기밀성은 TLS(wss://)가 담당한다.

2. 서버가 클라이언트로 보내는 프레임에는 왜 마스킹이 필요 없는가?

- 공격 방향이 반대이기 때문이다. 캐시 포이즈닝은 클라이언트가 보내는 바이트열이 프록시에게 HTTP 요청으로 오인되어 캐시 키가 오염되는 공격이다. 서버→클라이언트 방향에는 "프록시가 오인할 요청"이라는 게 성립하지 않는다. 게다가 서버는 신뢰 주체이지 브라우저에서 실행되는 공격자 스크립트가 아니다. 필요 없는 곳에 XOR 비용을 물리지 않는 것.

3. 마스킹 키가 헤더에 평문으로 실려 있는데도 방어가 성립하는 이유는?

- 방어의 대상은 "나중에 읽히는 것"이 아니라 "전송 시점에 원하는 바이트열을 만들어내는 것" 이기 때문이다. 공격자는 socket.send()에 넘길 페이로드는 정할 수 있지만, 브라우저가 프레임마다 랜덤 생성하는 키는 모른다. 따라서 회선에 실제로 나가는 바이트를 통제할 수 없다. 페이로드 통제와 바이트열 통제의 분리가 핵심이다.

4. 다음 프레임을 받았다. 어느 쪽이 보낸 것인가?

```
10000001  10000011  ...
```

- 둘째 바이트 10000011의 첫 비트가 MASK=1 → 클라이언트가 보낸 것이다. (참고로 payload length는 0000011 = 3바이트, 첫 바이트는 FIN=1 + opcode 0x1이므로 text 프레임)

5. 페이로드가 6바이트이고 마스킹 키가 4바이트일 때, 5번째 바이트에 적용되는 키 바이트는 몇 번째인가?

- i mod 4에서 i는 0부터 시작한다. 5번째 바이트는 i=4이므로 4 mod 4 = 0 → key[0], 즉 첫 번째 키 바이트다. 4개 주기로 순환하므로 5번째에서 다시 처음으로 돌아온다.

### 4. Fragmentation

#### 4-1. 구조

하나의 메시지를 여러 프레임으로 나눠 보내는 것. FIN 비트와 continuation opcode가 이걸 가능하게 한다.

3개 프레임으로 나눈 text 메시지:

| 순서          | FIN | opcode             | 의미                     |
| ------------- | --- | ------------------ | ------------------------ |
| 첫 프레임     | 0   | `0x1` text         | 타입 선언 + 아직 안 끝남 |
| 중간 프레임   | 0   | `0x0` continuation | 연장 + 아직 안 끝남      |
| 마지막 프레임 | 1   | `0x0` continuation | 연장 + 여기서 끝         |

두 필드가 독립적으로 다른 정보를 나른다.

- **opcode** — "이게 무슨 타입인가" (첫 프레임만 답한다)
- **FIN** — "여기서 메시지가 끝나는가"

continuation 프레임은 자기 타입을 갖지 않는다. 시퀀스 전체의 타입은 첫 프레임의 opcode가 결정한다. 첫 프레임이 `0x2` binary였으면 그 시퀀스는 binary 메시지다.

수신 측은 이 프레임들의 페이로드를 순서대로 이어붙여 하나의 메시지로 복원한다. 애플리케이션 레벨에서는 `onmessage`가 **한 번** 호출된다. 프레임 분할은 애플리케이션에게 보이지 않는다.

**프레임 하나로 끝나는 메시지**는 FIN=1 + opcode `0x1`(또는 `0x2`)이다. 이것을 unfragmented message라고 부른다.

#### 4-2. 왜 필요한가

**전체 길이를 모르는 상태에서 전송을 시작할 수 있다.**

프레임 헤더에는 payload length가 반드시 들어간다. 즉 프레임을 만들려면 길이를 먼저 알아야 한다. 스트리밍 상황에서는 이게 문제가 된다 — 파일을 읽으면서 보내거나, 서버가 생성 중인 데이터를 흘려보낼 때 최종 길이를 알 수 없다.

fragmentation이 있으면 확보된 만큼씩 프레임으로 내보내고, 데이터가 끝나는 시점에 FIN=1을 켜면 된다.

부수 효과: 거대한 메시지 전체를 메모리에 올려두지 않아도 된다.

#### 4-3. 순서 제약

**같은 방향에서 fragment 시퀀스가 진행 중일 때 다른 데이터 프레임을 끼워넣을 수 없다.**

메시지 A의 fragment를 보내는 도중에 메시지 B의 fragment를 섞어 보낼 수 없다. A가 FIN=1로 끝난 뒤에 B를 시작해야 한다.

이유는 구조적이다. 프레임 헤더에는 "몇 번째 메시지에 속하는가"를 나타내는 식별자가 없다. 섞여 오면 수신 측이 재조립할 방법이 없다.

> HTTP/2는 이 문제를 stream identifier를 프레임 헤더에 넣어서 해결했다. 그래서 멀티플렉싱이 된다. 웹소켓은 그 필드가 없어서 한 연결에서 한 번에 한 메시지만 진행할 수 있다.

**예외: 컨트롤 프레임은 끼어들 수 있다.**

```
text(FIN=0) → continuation(FIN=0) → ping → continuation(FIN=1)
```

이게 허용된다. 컨트롤 프레임은 메시지 조립 대상이 아니라 즉시 처리되는 관리용이므로 시퀀스를 방해하지 않는다.

이 예외가 없으면 거대한 메시지를 fragment로 보내는 동안 ping을 못 보내게 되고, 그 사이 연결이 죽어도 감지할 수 없다. 5장의 제약(125바이트 이하, 분할 불가)이 바로 이 예외를 안전하게 만드는 조건이다 — 컨트롤 프레임이 짧고 분할되지 않아야 시퀀스 중간에 끼어들어도 즉시 처리되고 끝난다.

#### 4-4. 위반 케이스

수신 측이 연결을 닫아야 하는 상황들:

- fragment 시퀀스 진행 중이 아닌데 `0x0` continuation 프레임을 받음
- fragment 시퀀스 진행 중에 `0x1`/`0x2` 데이터 프레임을 받음
- 컨트롤 프레임에 FIN=0이 설정됨

#### 4-5. 확인 문제

1. binary 메시지를 3개 프레임으로 나눠 보낼 때, 각 프레임의 FIN과 opcode는?

| 순서          | FIN | opcode |
| ------------- | --- | ------ |
| 첫 프레임     |     |        |
| 중간 프레임   |     |        |
| 마지막 프레임 |     |        |

- FIN: 0, 0, 1
- opcode: 0x2 binary, 0x0 continuation, 0x0 continuation
- 타입 선언은 첫 프레임에서 한 번만 한다. 나머지는 continuation이며, 시퀀스 전체의 타입은 첫 프레임의 opcode가 결정한다.

2. `onmessage` 핸들러는 위 3개 프레임에 대해 몇 번 호출되는가?

- **1번.** 프레임 분할은 프로토콜 레벨의 일이고, 수신 측이 페이로드를 이어붙여 하나의 메시지로 복원한 뒤 애플리케이션에 전달한다. 애플리케이션에게 fragmentation은 보이지 않는다.

3. fragment 시퀀스 중간에 ping을 보낼 수 있는 이유는?

- 컨트롤 프레임은 메시지 조립 대상이 아니라 즉시 처리되는 관리용 프레임이기 때문이다. 데이터 프레임 시퀀스에 끼어들어도 재조립을 방해하지 않는다. 이 예외가 필요한 이유는 반대로 생각하면 명확하다. 예외가 없으면 거대한 메시지를 fragment로 보내는 동안 ping을 보낼 수 없고, 그 사이 연결이 죽어도 감지하지 못한다.

4. 웹소켓이 한 연결에서 여러 메시지를 동시에 진행할 수 없는 구조적 이유는?

- **프레임 헤더에 메시지 식별자가 없기 때문.** 어느 메시지에 속한 프레임인지 구분할 방법이 없으므로, 여러 메시지의 fragment가 섞여 오면 수신 측이 재조립할 수 없다. HTTP/2는 stream identifier를 헤더에 넣어 이 문제를 해결했고 그래서 멀티플렉싱이 되지만, 웹소켓에는 그 필드가 없다.

5. 다음을 받았다. 문제가 있나?

```
프레임1: FIN=0, opcode=0x1
프레임2: FIN=0, opcode=0x2
```

- **문제가 있다.** 프레임1이 FIN=0이므로 fragment 시퀀스가 진행 중인데, 프레임2가 continuation(`0x0`)이 아니라 새로운 데이터 프레임(`0x2` binary)으로 왔다. 4-4의 위반 케이스에 해당하며, 수신 측은 연결을 닫아야 한다.

프레임2는 `FIN=0, opcode=0x0`이어야 했다.

### 5. 컨트롤 프레임 제약

#### 5-1. 두 가지 제약

```
1. 페이로드 125바이트 이하
2. 분할 불가 (항상 FIN=1)
```

대상은 `0x8` close, `0x9` ping, `0xA` pong. opcode 최상위 비트가 1인 것들.
(컨트롤 프레임은 프로토콜 동작의 정합성이 걸려 있어서 스펙이 못 박았고, 데이터 프레임은 운영 정책의 문제라 구현체에 위임했다.)

#### 5-2. 125라는 숫자의 근거

임의로 정한 값이 아니라 **1-3 분기표에서 역산된 값**이다.

| 7bit 값 | 의미                          |
| ------- | ----------------------------- |
| 0 ~ 125 | 길이 그 자체                  |
| 126     | 확장 길이 지시자 (16bit 추가) |
| 127     | 확장 길이 지시자 (64bit 추가) |

126과 127이 지시자로 예약되어 있으므로, **확장 길이 필드 없이 표현 가능한 최대값이 125**다.

즉 "125 이하"라는 제약은 실질적으로 **"컨트롤 프레임은 확장 길이 필드를 쓸 수 없다"** 는 뜻이다. 그 결과 컨트롤 프레임의 헤더 길이가 고정된다.

| MASK          | 헤더 길이 |
| ------------- | --------- |
| 0 (서버→클라) | 2바이트   |
| 1 (클라→서버) | 6바이트   |

데이터 프레임 헤더가 2~14바이트로 가변인 것과 대비된다. 컨트롤 프레임은 헤더를 읽는 순간 전체 길이가 확정된다.

#### 5-3. 왜 이런 제약을 걸었나

4-3의 예외 때문이다.

```
text(FIN=0) → continuation(FIN=0) → ping → continuation(FIN=1)
```

컨트롤 프레임은 fragment 시퀀스 중간에 끼어들 수 있다. 이 예외가 안전하려면 **끼어든 프레임이 즉시 처리되고 끝나야** 한다.

만약 컨트롤 프레임이 분할 가능하고 길이 제한이 없다면:

- ping이 여러 프레임으로 쪼개져 들어옴
- 수신 측은 ping 조립이 끝날 때까지 기다려야 함
- 그동안 원래 진행 중이던 데이터 시퀀스는 멈춤
- 컨트롤 프레임 시퀀스와 데이터 시퀀스가 동시에 진행되는 상태 → 4-3에서 본 대로 메시지 식별자가 없어 구분 불가

제약이 있으면 이 문제가 전부 사라진다. 컨트롤 프레임은 항상 프레임 하나로 완결되고, 짧아서 즉시 읽히며, 처리 후 원래 시퀀스로 복귀한다.

> **요약: 5장의 제약은 4-3의 예외를 성립시키기 위한 조건이다.** 두 규칙은 세트다.

#### 5-4. 부수 효과 — 라운드트립 측정

ping/pong의 페이로드가 짧다는 것은 하트비트 비용이 무시할 수준이라는 뜻이다.

pong은 받은 ping의 페이로드를 그대로 되돌려주도록 되어 있으므로, 125바이트 안에 타임스탬프나 시퀀스 번호를 넣어 보내면 그대로 돌아온다. RTT 측정과 응답 매칭에 쓸 수 있다.

#### 5-5. 위반 케이스

수신 측이 연결을 닫아야 하는 상황:

- 컨트롤 프레임 페이로드가 125바이트 초과
- 컨트롤 프레임에 FIN=0

#### 5-6. 데이터 프레임의 상한

컨트롤 프레임과 달리 스펙상 제한이 사실상 없다(2^63-1). 실질 상한은 구현체 설정이다.

| 구현체       | 옵션                | 기본값 |
| ------------ | ------------------- | ------ |
| ws (Node.js) | `maxPayload`        | 100MB  |
| Socket.IO    | `maxHttpBufferSize` | 1MB    |

제한하는 이유는 DoS 방어다. 수신 측은 payload length를 읽고 그만큼 버퍼를 할당하므로, 상한이 없으면 거대한 길이를 선언하는 것만으로 메모리를 고갈시킬 수 있다.

초과 시 서버는 close code `1009` (Message Too Big)로 연결을 닫는다.

#### 5-7. 확인 문제

1. 컨트롤 프레임 페이로드 상한이 왜 하필 125인가?

2. 컨트롤 프레임의 헤더 길이는 항상 몇 바이트인가? 두 경우로 나눠 답하라.

3. 컨트롤 프레임이 분할 불가여야 하는 이유를 4-3과 연결해서 설명하라.

4. 다음 프레임은 유효한가?

```
FIN=0, opcode=0x9, payload length=10
```

5. 다음 프레임은 유효한가?

```
FIN=1, opcode=0x8, payload length=130
```

**1.** 7bit payload length 필드에서 126과 127이 확장 길이 지시자로 예약되어 있기 때문이다. 확장 필드 없이 표현 가능한 최대값이 125이므로, 이 제약은 실질적으로 "컨트롤 프레임은 확장 길이 필드를 쓸 수 없다"는 뜻이다.

**2.** MASK=0(서버→클라이언트)이면 **2바이트**, MASK=1(클라이언트→서버)이면 **6바이트**. 확장 길이 필드가 없으므로 데이터 프레임과 달리 가변이 아니다.

**3.** 컨트롤 프레임은 fragment 시퀀스 중간에 끼어들 수 있는데(4-3의 예외), 이게 안전하려면 끼어든 프레임이 즉시 처리되고 끝나야 한다. 분할 가능하면 컨트롤 프레임 조립이 끝날 때까지 데이터 시퀀스가 멈추고, 두 시퀀스가 동시에 진행되는 상태가 된다. 웹소켓 프레임 헤더에는 메시지 식별자가 없으므로 이 상태를 구분할 수 없다. 즉 5장의 제약은 4-3의 예외를 성립시키기 위한 조건이다.

**4.** **유효하지 않다.** opcode `0x9`는 ping, 즉 컨트롤 프레임인데 FIN=0이다. 컨트롤 프레임은 분할 불가이므로 항상 FIN=1이어야 한다. 수신 측은 연결을 닫아야 한다. (payload length 10은 125 이하이므로 문제없다)

**5.** **유효하지 않다.** opcode `0x8`은 close, 즉 컨트롤 프레임인데 payload length가 130으로 125를 초과했다. 애초에 130은 7bit 필드로 표현할 수 없어 확장 길이 필드가 필요한데, 컨트롤 프레임은 그걸 쓸 수 없다. 수신 측은 연결을 닫아야 한다.

</details>

### 6. Close handshake와 close code

#### 6-1. 종료는 양방향이다

TCP 연결을 그냥 끊는 것이 아니라, close 프레임을 주고받은 뒤 끊는다.

```
A: close 프레임 전송  →
                      ←  B: close 프레임 응답
A: TCP 연결 종료
```

절차:

1. 한쪽이 close 프레임(`0x8`)을 보낸다. 이 시점부터 그쪽은 **더 이상 데이터 프레임을 보내지 않는다**
2. 받은 쪽은 close 프레임으로 응답한다. 이미 close를 보낸 상태라면 다시 보내지 않는다
3. close 프레임을 **먼저 보낸 쪽이** TCP 연결을 닫는다. 서버가 먼저 닫아야 TIME_WAIT 부담이 서버 쪽에 남는 것을 제어할 수 있다

close 프레임을 받았지만 아직 응답을 보내지 않은 상태에서는, 이미 수신 중이던 데이터를 처리하는 것까지는 허용된다.

#### 6-2. close 프레임의 페이로드

```
[2바이트] 상태 코드 (부호 없는 정수, big-endian)
[N바이트] 사유 문자열 (선택, UTF-8)
```

페이로드 전체를 생략할 수도 있다. 이 경우 코드 없이 종료된 것으로 처리한다.

컨트롤 프레임이므로 5장의 제약을 받는다 — 페이로드 총 125바이트 이하, 따라서 사유 문자열은 최대 123바이트.

#### 6-3. 주요 close code

| 코드   | 이름                 | 의미                                |
| ------ | -------------------- | ----------------------------------- |
| `1000` | Normal Closure       | 목적을 다하고 정상 종료             |
| `1001` | Going Away           | 서버 종료, 페이지 이탈              |
| `1002` | Protocol Error       | 프로토콜 위반 감지                  |
| `1003` | Unsupported Data     | 처리할 수 없는 타입의 데이터        |
| `1006` | Abnormal Closure     | **close 프레임 없이 연결이 끊김**   |
| `1007` | Invalid Payload Data | text 프레임인데 유효하지 않은 UTF-8 |
| `1009` | Message Too Big      | 수신 측 크기 제한 초과              |
| `1011` | Internal Error       | 서버 내부 오류                      |

`1000`~`2999`는 스펙 예약 구간, `3000`~`3999`는 라이브러리/프레임워크용, `4000`~`4999`는 애플리케이션 자유 사용 구간이다.

#### 6-4. 1006의 특수성

**`1006`은 회선을 통해 전송되지 않는 코드다.**

의미가 "close 프레임을 받지 못한 채 연결이 끊겼다"이므로, 프레임에 실려 올 수가 없다. 프레임이 왔다면 그건 1006이 아니다.

이 값은 수신 측이 **로컬에서 감지해 채워 넣는다.** TCP 연결이 close handshake 없이 끊긴 것을 관찰하고, `CloseEvent.code`에 1006을 넣어 애플리케이션에 전달한다.

이것이 오늘 노트에서 실무적으로 가장 중요한 지점이다. 클라이언트 입장에서 두 상황은 완전히 다르다.

|             | 클라이언트가 아는 것         | 대응                            |
| ----------- | ---------------------------- | ------------------------------- |
| `1000` 수신 | 상대가 **의도적으로** 닫았다 | 재연결하지 않는 게 맞을 수 있음 |
| `1006`      | 왜 끊겼는지 **모른다**       | 재연결 시도 대상                |

`1006`이 나오는 실제 상황: 네트워크 단절, 서버 프로세스 강제 종료, 프록시 타임아웃, 모바일 네트워크 전환.

#### 6-5. wasClean

브라우저 `CloseEvent`에는 `wasClean` 플래그가 있다. close handshake가 정상적으로 완료되었는지를 나타낸다.

```js
socket.onclose = (event) => {
  console.log(event.code, event.reason, event.wasClean);
};
```

`wasClean === false`이면 코드는 대개 `1006`이다. 재연결 로직의 분기 조건으로 쓰인다.

#### 6-6. 확인 문제

1. close handshake가 양방향인 이유는?

2. close 프레임의 사유 문자열이 최대 123바이트인 이유는?

3. `1006`이 회선으로 전송되지 않는 이유는?

4. 재연결 로직을 짤 때 `1000`과 `1006`을 왜 구분해야 하는가?

5. 다음은 유효한 close 프레임인가?

```
FIN=1, opcode=0x8, payload = [0x03, 0xE8]
```

---

<details>
<summary>답</summary>

**1.** 양쪽이 서로 더 이상 데이터를 보내지 않는다는 것을 명시적으로 합의하기 위해서다. 한쪽이 일방적으로 TCP를 끊으면 상대는 전송 중이던 데이터가 유실됐는지 알 수 없고, 정상 종료인지 장애인지도 구분할 수 없다. close 프레임을 주고받으면 그 구분이 생긴다 — 이것이 `1000`과 `1006`을 가르는 지점이다.

**2.** close 프레임은 컨트롤 프레임이므로 페이로드가 125바이트 이하여야 한다(5장). 앞의 2바이트가 상태 코드이므로 사유 문자열에 남는 것은 123바이트다.

**3.** `1006`의 의미가 "close 프레임을 받지 못했다"이기 때문이다. 프레임에 실려 온다면 그것 자체가 close 프레임을 받았다는 뜻이 되어 모순이다. 수신 측이 TCP 단절을 관찰하고 로컬에서 채워 넣는 값이다.

**4.** `1000`은 상대가 의도적으로 닫은 것이므로 재연결이 불필요하거나 오히려 잘못된 동작일 수 있다. `1006`은 원인을 알 수 없는 단절이므로 재연결 대상이다. 이 구분 없이 무조건 재연결하면, 서버가 명시적으로 종료한 세션에 클라이언트가 계속 들이받는 상황이 생긴다.

**5.** 유효하다. `0x03E8` = 1000 = Normal Closure. 컨트롤 프레임이고 FIN=1, 페이로드 2바이트로 125 이하다. 사유 문자열 없이 코드만 담은 정상적인 close 프레임이다.

</details>

### 7. smocket 연결 고리 (개인 메모)

오늘 배운 것이 그대로 fault injection API 목록이 된다.

#### 7-1. 대응표

| 오늘 배운 것           | smocket에서                                                                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `1000` vs `1006`       | 끊김 시뮬레이션의 두 종류. close 프레임을 보내고 끊는 것과 안 보내고 끊는 것은 클라이언트 입장에서 완전히 다른 이벤트다. 재연결 로직 테스트의 최소 단위 |
| ping/pong              | 하트비트 타임아웃 재현 지점. pong을 지연시키거나 누락시켜 클라이언트 타임아웃 처리를 검증                                                               |
| fragmentation          | 패킷 순서 뒤바뀜을 주입할 때 건드리는 층. 프레임 경계를 알아야 무엇을 재배열할지가 정의된다                                                             |
| 프레임 = 전송 단위     | "패킷 손실"의 손실 단위가 프레임이다. 프레임을 모르면 지연/손실 주입이 setTimeout 수준에 머문다                                                         |
| `1009` Message Too Big | `maxHttpBufferSize` 초과 상황 재현. 클라이언트가 같은 데이터를 재전송하며 무한루프에 빠지는지 검증                                                      |
| 마스킹 방향 규칙       | 서버 시뮬레이터로서 보내는 프레임은 MASK=0이어야 한다. 프로토콜 충실도(Lv.1) 요구사항                                                                   |

#### 7-2. 층위 구분 — 어디를 조작할 것인가

오늘 배운 ping/pong은 **웹소켓 프로토콜 레벨**이다. Socket.IO의 하트비트는 **Engine.IO 레벨**의 별개 메커니즘이다. 두 층이 겹쳐 있다.

```
Socket.IO      ← 이벤트, 룸, 네임스페이스
Engine.IO      ← 자체 ping/pong, 트랜스포트 폴백
WebSocket      ← 오늘 배운 프레임, 0x9/0xA ping/pong
TCP
```

smocket이 Socket.IO 서버 시뮬레이터인 이상, 하트비트 타임아웃을 재현하려면 **어느 층의 ping/pong을 조작할지 먼저 정해야 한다.** 브라우저 `WebSocket` API에는 ping을 보내는 메서드가 없으므로, 클라이언트 측에서 관측되는 하트비트는 대부분 Engine.IO 레벨이다.

#### 7-3. 도출되는 API 초안

```
disconnect({ clean: true })   → close(1000) 프레임 전송 후 종료
disconnect({ clean: false })  → 프레임 없이 종료 → 클라이언트에 1006
disconnect({ code: 1009 })    → 특정 코드로 종료
heartbeat({ dropPong: true }) → pong 미응답
heartbeat({ delay: 5000 })    → pong 지연
```

핵심은 `clean` 플래그다. 이 한 개의 옵션이 "재연결 로직이 정상 종료와 비정상 단절을 구분하는가"를 테스트한다 — 실제로 많은 클라이언트 코드가 이 구분 없이 무조건 재연결한다.

### 8. 오늘의 한 문장

> ⭐️ 웹소켓 프레임은 TCP 바이트 스트림 위에 경계를 긋는 층이고, 그 경계가 곧 fault injection의 단위다.

## 면접용 1분 답변

**Q. WebSocket 프레임 구조에 대해 설명해주세요.**

WebSocket이 프레임이라는 단위를 두는 이유는 TCP가 바이트 스트림이기 때문입니다. TCP는 순서와 도달만 보장하고 메시지 경계는 알려주지 않아서, 그 위에 자체 경계를 정의해야 합니다.

프레임은 헤더와 페이로드로 구성됩니다. 헤더 첫 바이트에 FIN 비트와 opcode가 들어갑니다. FIN은 이 프레임에서 메시지가 끝나는지를 나타내고, opcode는 프레임의 종류를 나타냅니다. text, binary, continuation이 데이터 프레임이고 close, ping, pong이 컨트롤 프레임인데, opcode 최상위 비트가 1이면 컨트롤 프레임이라 비트 하나로 분류가 가능합니다.

둘째 바이트에는 MASK 비트와 payload length 7비트가 들어갑니다. 7비트로는 125까지만 표현되고, 126과 127은 뒤에 확장 길이 필드를 더 읽으라는 지시자입니다. 그래서 헤더 길이가 최소 2바이트에서 최대 14바이트로 가변입니다.

마스킹은 클라이언트에서 서버 방향에서만 의무입니다. 암호화가 아니라 캐시 포이즈닝 방어가 목적입니다. 웹소켓을 모르는 중간 프록시가 페이로드를 HTTP 요청으로 오인해 캐시를 오염시키는 공격이 가능했는데, 프레임마다 랜덤 키로 XOR하면 공격자가 페이로드는 정해도 회선에 나가는 바이트열은 통제할 수 없게 됩니다.

FIN을 0으로 두고 continuation 프레임을 이어붙이면 하나의 메시지를 여러 프레임으로 나눌 수 있습니다. 전체 길이를 모르는 상태에서 전송을 시작할 수 있게 하기 위한 구조입니다. 이때 컨트롤 프레임만 시퀀스 중간에 끼어들 수 있는데, 이걸 안전하게 만들려고 컨트롤 프레임에 125바이트 이하, 분할 불가라는 제약이 걸려 있습니다.

---

**Q. 실무에서 이게 왜 중요한가요? (꼬리질문 대비)**

close code 처리에서 직접 드러납니다. 정상 종료는 close 프레임을 주고받고 끊기 때문에 1000번 코드가 오지만, 네트워크 단절이나 서버 강제 종료처럼 close 프레임 없이 끊기면 1006이 됩니다.

1006은 회선으로 전송되지 않는 코드입니다. "close 프레임을 못 받았다"는 의미라서 프레임에 실려 올 수가 없고, 클라이언트가 TCP 단절을 감지해 로컬에서 채워 넣는 값입니다.

이 구분이 재연결 로직의 분기점입니다. 1000은 상대가 의도적으로 닫은 것이라 재연결이 오히려 잘못된 동작일 수 있고, 1006은 원인을 모르는 단절이라 재연결 대상입니다. 실제로 이 구분 없이 무조건 재연결하는 코드가 많습니다.

저는 이걸 테스트하려고 smocket이라는 Socket.IO 서버 시뮬레이터를 만들고 있는데, `disconnect({ clean: true/false })` 옵션 하나가 정확히 이 두 상황을 재현합니다. 프레임 구조를 이해하지 못하면 이런 fault injection이 그냥 setTimeout 수준에 머물게 됩니다.

## 한 줄 요약

> WebSocket 프레임은 TCP 바이트 스트림 위에 메시지 경계를 긋는 층이고, FIN·opcode·MASK·payload length라는 헤더 필드가 그 경계와 종류를 정의한다. 그리고 그 경계가 곧 fault injection의 조작 단위가 된다.
